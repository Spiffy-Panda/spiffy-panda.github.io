Ostranaut Data Explorer

A “find everywhere this is used” index for a space-sim whose entire content layer is loose JSON with no foreign keys. I built it, then built three measurements to judge it, and all three turned out to be measuring something other than what I thought.

github.com/Spiffy-Panda/Ostranaut-Explorer Own the game? Clone it, run make, point it at your install — you get the real index C# · .NET 8 · vanilla JS · no framework, no server

Real data, today’s build. The four things that happen to you when you lie down in Ostranauts, and where each one points. One target sits exactly where it claims. Three are reported broken — but two of those name things the engine makes up at runtime and never writes to disk, so they are correct and will fail forever. The only real bug here is the third, whose target exists perfectly well one folder over.

What it is, and who it is for

If you have ever changed a recipe or a trait by editing a game’s data files, this is built for you. If you have not, the next four paragraphs are the whole idea.

Ostranauts keeps its content in 440 JSON files across 71 folders. Every entry has a unique name — the field is literally called strName — and entries refer to each other by writing that name as a plain string. There is no type on it. Nothing checks that the name is real. A string is a reference because a human knows it is one, and if you rename something, the breakage shows up an hour later in-game as a piece of furniture that will not open.

So the usual way to change anything is to search for a name and read everything that comes back. That is slow, and it misses every place the name is buried inside a longer string, which in this data is most places. A weight of 0.75 and a duration of x1 are packed into the same string as the name they modify.

This project reads all of it once, works out what points at what, and puts it on a page you click through. Pick any entry and see everything it references and everything that references it, with the packed values pulled apart and shown on each row. It is the button your code editor gives you for free when you rename a function, built for a pile of text no editor understands.

Three words appear throughout and they are the only vocabulary you need. A reference is one place where an entry names another; there are 165,988. A reference is dangling when the thing it names does not exist. A folder is the directory an entry lives in, which doubles as its category and is half of its identity — and that last detail turns out to be where everything goes wrong.

The rest of this page is about the going wrong. I built three ways to measure whether the index was any good. All three were broken, in three different ways, and finding that out taught me more than building the index did.

01

How the index is built, and why it has to be repeatable

No hand-written extraction rules. The extractor learns what points where by reading the game’s own schema files, and the same input has to produce the same output or none of the measurements below mean anything.

The obvious build is a lookup table: for each folder, hand-write which fields point where. That table is wrong the day the game patches, and it makes the tool a maintenance burden rather than a thing you run. So the extractor derives its rules instead. It reads the prose in each field’s description and decides from that whether the field carries a reference and into which folder.

That one description produces 11,169 references, each keeping its parsed value and duration rather than throwing them away — which is what lets a condition’s own page later say “default 1.0 across 340 owners, modified by ±0.2 across 88 interactions.” 170 rules of this kind cover the tree. The game ships five schemas for about seventy folders, so where there is no schema a generator writes one by reading the game’s decompiled loader classes for the field names.

Same input, same bytes

This is not housekeeping. It is the precondition for everything in section 02: you cannot say a number changed because of a code change if two runs of the same code disagree. I ran the builder twice into separate directories and hashed both sets of output.

The load-bearing caveat

“The name exists in another folder” is not proof the reference should point there. Names are reused across folders on purpose in this data, and the build reports 15 duplicate-name warnings within single folders alone. I am confident about the two condition folders because the game’s own loader reads both into one namespace. I am not confident about loot → cooverlays, 2,485 references, which I have not checked against the loader and which could be genuine name reuse. So 27,259 is an upper bound on mis-filing and 5,533 is a lower bound on true absence.

The part that should have been the headline

This exact fix already exists in the codebase. A phase of the code-side work added a step that retargets a reference from conditions/ to conditions_simple/ when the name is found there. I scoped it to one kind of reference, of which there are 38, and never generalised it to the other 165,950.

A fix that covers 38 of 165,988 cases is a fix that will be quietly wrong for four months, and it was. That is the actual failure on this page, and I first wrote it up as an aside.

You can see the consequence on the page a modder reads. Red italic means “this target does not exist.”

One more thing the split turned up, which I am reporting because it is interesting and not because it means what it looks like. Sorting by where each rule came from, the machine-generated rules dangle at 10.2% and the hand-written ones at 24.9%. These are exact counts over every reference in the build, not estimates from a sample, so there is no interval and no chance of a fluke. But the two groups are not comparable populations: the hand-written group contains the two condition folders and therefore inherits the entire mis-filing problem above. Nothing here supports “generated rules are better.” It supports “the fields humans bothered to describe are the hard ones,” which is a different and much less flattering claim.

03

What the corrected measure found: one sentence, 1,979 invented references

Once the truly-absent group was separated out, I sorted it by which field produced it — a column I had never sorted in four months of the dashboard being on screen. The top row was interactions.strTargetPoint: 1,979 references, 100.0% unresolvable. A field where every single reference fails is not a data problem. It is a rule that should not exist.

The value is not a condowner’s name. It is the label of an anchor point defined inside a condowner, one level down in a different namespace. So the extractor had spent four months confidently inventing two thousand connections that do not exist, on the strength of one clause in one description that I believed. Nine values carry all 1,979:

That shape check is the fix, and it generalises: any rule whose emitted values do not look like entry names, and any rule whose failure rate sits at 0% or 100%, is a rule that is wrong rather than a rule with extreme data. Neither check exists yet. As of this build the extractor still emits all 1,979, and the honest reading is that I wrote the diagnosis down instead of making the build hold it — which is the same habit as scoping the retarget to 38 cases.

The opposite case sits in the same 3.3% bucket. 729 references point at names starting Thresh, which the engine synthesises at runtime and never writes to disk. Those are correct and will dangle forever; the site already renders them as a derived panel rather than as breakage. Two populations, one number, opposite meanings. Which is the argument for never shipping the aggregate on its own.

04

The second measure: it could not move

One folder ships as a single flat array where every seven consecutive strings form one record. Expanding it created 1,390 new entries that dozens of previously-dangling references had been pointing at. I expected a visible drop in dangling and a rise in resolved references. I hit build and the number did not move a single tick, and my first thought was that I had broken the builder.

The reason is that resolution had a fallback. Those references were already being emitted and already counted; they just pointed at nothing. Giving them somewhere to land changed where they pointed without changing how many there were. The number I was watching was structurally incapable of showing the improvement I had just made, and equally incapable of showing the regression if I had broken it instead.

That is the section 02 failure one level up: a total that moves for reasons unrelated to the thing it is being used to judge. It is why the dangling check is now a separate pass that resolves every reference independently, rather than a counter incremented while extracting. Worth being precise about what the zero could not tell me, though: a flat total is equally consistent with nothing happening and with a thousand things happening and cancelling. I worked out the mechanism by reading the fallback code, not by measuring, which means the measurement as taken was worthless.

05

The third measure: it looked healthy

A correct index is not a usable one, and nothing in sections 01 to 04 can tell the difference. So the site gets walked. An LLM agent drives a real browser through Playwright — navigate, click, screenshot, one capture per step — against the live site with no access to the source, no URL editing, and no knowledge of where the answer lives. It is handed a written scenario and it records where it stops. The first walk failed.

The scenario: a modder wants a pair of in-game leggings to protect against blacking out under heavy burn, and needs to find the entry that connects the garment to the effect. The site got the agent to the right page. Then a sidebar listing every entry that shifts that stat’s thresholds cut its list at six, sorted alphabetically, with a dead + 6 more line and no way to expand it. A display cap and an alphabetical sort are each defensible alone. Together they made a page that was confidently, silently wrong for one specific reader — and a screenshot of that page looks completely healthy, which is why every check I had passed it. The walk caught it because it pursued the task rather than inspecting the interface.

One walk, one scenario, one run

This finds a failure that is present. It says nothing about how often failures like it occur, and it cannot detect anything the scenario did not happen to touch. There is no baseline, no scoring rubric fixed before the run, and no repeat run — and since the agent is stochastic, a single trajectory cannot separate “the site is unnavigable here” from “this run went badly.” “The site fails newcomers” is not a supported claim. “The site failed this walk here, for this reason, at this line” is. Turning it into a real measurement means a suite of scenarios, a fixed success criterion, several runs each, and a regression test that fails when the sidebar hides a grant — none of which exists yet.

What I cannot claim

You cannot verify any of this by clicking the link. The deployment that runs in CI writes an empty index on purpose, because the game’s content is not mine to redistribute, so the live page demonstrates the interface and not the data. Every figure here comes from a local build against a licensed install. If you own the game, cloning the repository and running make gets you the real thing; if you do not, you are taking my word for it. A synthetic sample corpus checked into the repository would fix that and does not exist yet.

Three defects are disclosed here and none are fixed. The 1,979 invented references, the retarget scoped to 38 cases out of 165,988, and the sidebar cap. Each has a known fix and a rough cost measured in hours. Alongside them, two of the game’s 440 JSON files are rejected by the parser and skipped on every build, because they use a backslash-apostrophe escape the reader rejects and the game accepts. It is printed in the build log and has never been handled.

The pattern is the same one the page is about. The project’s own architecture summary still states 87,845 references and 91 rules against today’s 165,988 and 170, and the repository has a written rule requiring that file be updated before every commit. The rule was written down; no check enforces it. Written rule, no mechanism — four times over, including twice where the diagnosis was already correct and sitting in a file.

Scope. This is single-machine data engineering, a static frontend, and one stubborn habit of not believing the tool’s self-report. There is no model training here and no distributed system. The transferable part, if there is one, is that determinism is what makes attribution possible, that a total which cannot move is not a measurement, and that a rule failing at exactly 0% or 100% is telling you about the rule.
